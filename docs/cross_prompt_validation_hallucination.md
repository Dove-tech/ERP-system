# 多 Prompt 交叉验证与幻觉治理

本文档整理“在工具选择和参数抽取阶段使用三套 prompt 做交叉验证，是否可以降低幻觉概率，以及如何落地”的面试回答口径。

## 1. 结论

三套 prompt 交叉验证可以降低某些类型的幻觉概率，但不能消除幻觉，也不能替代确定性校验。

准确说法是：

```text
多 prompt 交叉验证是模型侧的风险降低手段。
它可以降低工具误选、意图过度扩展、参数凭空补全等模型侧错误。
但它不是安全边界。
最终仍然必须依赖候选白名单、schema 校验、实体解析、权限校验、HITL、trace 和 eval。
```

不要说：

```text
用了三套 prompt 就不会幻觉。
```

推荐说：

```text
三套 prompt 从不同角度审查同一个 ToolCallProposal，可以降低单一 prompt 偏差导致的幻觉概率。
```

## 2. 为什么多 Prompt 可能有效

如果只是把同一个问题换三种说法问三遍，价值不大。

有效的交叉验证不是简单重复，而是让三套 prompt 扮演不同角色：

```text
Prompt A：业务语义匹配
判断用户真实业务动作和候选工具是否匹配。

Prompt B：风险与越权审计
判断模型是否把用户意图过度扩展成导出、发送、删除、批量更新等高风险动作。

Prompt C：参数可执行性检查
判断参数是否真实来自 query、上下文或工具结果，是否缺参、歧义或凭空补全。
```

这样做的价值是：

```text
同一个工具调用建议需要同时通过业务语义、风险审计和参数可执行性三个维度。
如果某一路 prompt 发现明显异常，就可以阻止系统直接执行。
```

## 3. 三套 Prompt 分别防什么

### 3.1 Prompt A：业务语义匹配

关注点：

```text
用户到底想做什么业务动作。
工具的业务对象是否匹配。
是否因为字段相似选错工具。
```

典型防护：

```text
查订单却选库存工具。
查库存却选商品档案工具。
查对账单却选客户信息工具。
查询订单主表和订单明细混淆。
```

示例：

```text
用户：查询订单 O-9001

错误工具：query_inventory
正确工具：query_order
```

Prompt A 会重点看：

```text
业务动作 = 查询
业务对象 = 订单
```

而不是只看候选工具里都出现了 `productId`。

### 3.2 Prompt B：风险与越权审计

关注点：

```text
用户是否明确表达了高风险动作。
模型是否把查询扩展成导出、发送邮件、删除、批量更新。
工具动作是否超出用户原始意图。
```

典型防护：

```text
用户只说查询，模型选择导出。
用户只说导出，模型扩展成发送邮件。
用户只说查看订单，模型选择更新订单。
用户没有说删除，模型选择删除工具。
```

示例：

```text
用户：查一下华东区大客户上个月的对账单。

错误工具：send_reconciliation_email
正确工具：query_reconciliation
```

Prompt B 会判断：

```text
用户没有表达“发送邮件”。
外发动作属于高风险。
应阻断或澄清。
```

### 3.3 Prompt C：参数可执行性检查

关注点：

```text
参数是否足够。
参数是否来自用户 query、近期对话、工具返回结果或已确认信息。
模型是否凭空补 productId、supplierId、customerId、quantity、date_range。
自然语言实体是否需要解析。
```

典型防护：

```text
用户没说供应商，模型补 supplierId。
用户说“苹果”，模型直接当成唯一 productId。
用户说“上个月”，模型没有根据系统时间转换日期范围。
用户给了模糊客户名，模型直接生成 customerId。
长期记忆被误当成强参数。
```

示例：

```text
用户：帮我创建苹果订单，数量 50。

缺失参数：supplierId
风险：模型可能凭空补一个供应商。
```

Prompt C 应返回：

```text
need_clarification
missing_params = ["supplierId"]
```

而不是自己补一个供应商 ID。

## 4. 能降低哪些幻觉

### 4.1 工具幻觉

工具幻觉是指模型选择了不该选择的工具，或者试图选择不存在的工具。

示例：

```text
用户：查询华东区大客户上个月对账单。
模型：send_email
```

交叉验证中：

```text
Prompt A 会认为业务动作不匹配。
Prompt B 会认为用户没有表达发送邮件。
Prompt C 可能发现缺少收件人参数。
```

最终不会直接执行 `send_email`。

### 4.2 意图扩展幻觉

意图扩展幻觉是指模型把用户没有说的动作补出来。

示例：

```text
用户：导出上个月华东区大客户对账单。
模型：导出并发送给财务负责人。
```

Prompt B 会拦截：

```text
用户只表达了导出，没有表达发送邮件。
发送邮件属于外发动作。
需要澄清或阻断。
```

### 4.3 参数幻觉

参数幻觉是指模型生成了用户没有提供、系统也没有证据支持的参数。

示例：

```text
用户：帮我创建苹果订单，数量 50。
模型：supplierId = SUP-A
```

Prompt C 会检查：

```text
supplierId 是否来自当前 query？
是否来自用户本轮补充？
是否来自已确认工具结果？
是否只是长期偏好？
```

如果没有强来源，应进入缺参澄清或 HITL 明确确认。

### 4.4 no_tool 场景误触发

示例：

```text
用户：写一首关于春天的诗。
```

Prompt A 和 Prompt B 都可能返回：

```text
no_tool
```

从而减少系统硬选业务工具。

## 5. 不能解决哪些幻觉

多 prompt 交叉验证不是万能的。

以下情况仍然可能一起错：

```text
1. 三套 prompt 都被同一个错误上下文误导。
2. 工具描述本身写错或边界不清。
3. RAG 召回候选里没有正确工具。
4. 权限数据或用户身份上下文错误。
5. 三套 prompt 都误认为“苹果”唯一指苹果手机 A15。
6. 模型供应商本身输出不稳定。
7. 工具 schema 不准确，导致参数判断错误。
```

所以多 prompt 交叉验证之后仍然必须有确定性校验：

```text
候选工具白名单
function_name 白名单
JSON Schema 校验
required 参数校验
实体解析
工具权限校验
数据权限校验
HITL
后端 API 二次鉴权
trace 和 eval
```

## 6. 为什么不能只是同一个 Prompt 问三遍

如果三套 prompt 都是：

```text
请选择最合适的工具。
```

然后只是换几个词，这种方案价值有限。

原因是：

```text
三次调用可能共享同样的偏差。
成本和延迟增加。
输出冲突后难以解释。
没有针对不同错误类型做防护。
```

真正有效的是分工：

```text
一个看业务语义。
一个看风险边界。
一个看参数可执行性。
```

这叫增加判断维度，而不是简单多数投票。

## 7. 推荐输出结构

三套 prompt 都通过 function call 输出统一结构：

```json
{
  "decision": "call_tool",
  "tool_name": "query_reconciliation",
  "arguments": {
    "region": "华东区",
    "customer_type": "大客户",
    "date_range": "上个月"
  },
  "missing_params": [],
  "risk_flags": [],
  "reason": "用户明确要求查询华东区大客户上个月对账单"
}
```

推荐字段：

```text
decision:
call_tool / no_tool / need_clarification / reject

tool_name:
候选工具名称。

arguments:
候选参数。

missing_params:
缺失参数。

risk_flags:
高风险动作、外发、删除、批量、越权等标记。

reason:
简短理由，便于 trace 和人工复盘。
```

## 8. 聚合规则

推荐聚合策略：

```text
普通 read 查询：
2/3 选择同一个 tool_name，且没有 reject，可以进入校验。

写操作 / 导出 / 发送 / 删除：
至少 2/3 同意，且 Prompt B 不能 reject。

删除 / 批量更新 / 外发邮件：
建议 3/3 同意，或者必须进入人工确认。

两票 no_tool：
返回 no_tool_found。

两票 need_clarification：
向用户澄清。

三票工具不一致：
不强行选择，进入澄清或人工接管。

Prompt C 认为必填参数缺失：
即使 Prompt A/B 选择工具，也不能进入执行，只能澄清。
```

## 9. 参数合并原则

不要简单拿某一个 prompt 的 arguments。

推荐字段级合并：

```text
多个 prompt 给出相同值 -> 可作为候选参数。
只有一个 prompt 给出的关键参数 -> 检查来源。
参数冲突 -> 澄清。
必填参数缺失 -> 澄清。
长期记忆来源参数 -> 必须展示给用户确认。
```

示例：

```text
Prompt A：quantity = 100
Prompt B：quantity = 100
Prompt C：quantity = 50
```

不能直接执行，应向用户澄清：

```text
检测到数量参数不一致，请确认数量是 50 还是 100。
```

## 10. 与 Harness 的关系

多 prompt 交叉验证只是 harness 中的一层。

完整链路应是：

```text
RAG 召回候选工具
-> rerank 精排
-> 权限预过滤
-> 三套 prompt/function call 生成 ToolCallProposal
-> 聚合投票
-> 候选工具白名单校验
-> JSON Schema 校验
-> 实体解析
-> 数据权限校验
-> HITL
-> API 执行
-> trace / eval
```

也就是说：

```text
三套 prompt 降低模型侧幻觉。
确定性校验提供工程安全边界。
HITL 提供人工确认。
trace/eval 提供持续改进闭环。
```

## 11. 面试表达

可以这样回答：

> 三套 prompt 交叉验证可以降低幻觉概率，但我不会把它当成唯一防线。它主要降低工具误选、意图过度扩展、参数凭空补全这类模型侧幻觉。关键是三套 prompt 不能重复问同一个问题，而是分别从业务语义、风险审计、参数可执行性三个角度审查同一个 function call proposal。

继续补充：

> 普通查询可以 2/3 多数通过，高风险工具要求更严格，比如风险审计 prompt 不能 reject；删除、批量更新、外发邮件这类动作会要求更严格的投票或强制 HITL。最后仍然必须经过候选工具白名单、schema 校验、实体解析、权限校验和 HITL，因为交叉验证只能降低模型错误概率，不能提供确定性安全保证。
