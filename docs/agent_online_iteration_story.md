# Agent 项目上线后的持续迭代故事

本文档是一套面试中可以讲述的项目上线与持续迭代故事。重点不是罗列功能，而是展示：我参与了 Agent 项目的真实开发、上线、问题定位、技术改造、评测闭环和复盘。

故事背景可以包装为：

```text
项目周期：2025.09 - 2025.12
项目类型：企业内部零售供应链 ERP Copilot 试点
业务对象：产品、库存、订单、物流供应商、对账单、生产计划
用户对象：运营、供应链专员、客服支持、财务对账人员
核心目标：让业务人员用自然语言完成 ERP 查询和部分低频操作，同时保留权限、人工确认和审计链路
```

一句话概括：

> 这个项目不是做一个完全自主的通用 Agent，而是在企业 ERP 场景里做一个可控型业务 Copilot。上线之后，我们遇到的主要问题不是“模型不会回答”，而是工具误触发、参数抽取不稳、多步骤链路容易跑偏、HITL 用户反馈理解不足、RAG 工具召回相似工具混淆、上下文串用、权限和高风险动作控制不够细。我的工作重点是把这些 bad case 变成 trace、eval、prompt、guardrail 和工作流改造。

## 1. 上线前的初始版本

### 1.1 初始能力

第一版上线时，系统已经具备：

```text
OpenAPI 工具注册
工具描述向量化召回
LLM 工具选择
参数抽取
工具调用
人工确认 HITL
最终结果总结
基础前端对话界面
```

当时的主要链路是：

```text
用户自然语言
-> 任务判断
-> 工具召回
-> LLM 选择工具
-> 参数抽取
-> 人工确认
-> 调用 ERP API
-> 总结结果
```

这个版本能跑 demo，也能覆盖一些简单场景，例如：

```text
查询苹果的库存
查询订单 O-9001
帮我创建产品 1001、数量 20、供应商 3 的订单
```

### 1.2 上线后的真实反馈

上线给小范围运营团队试用后，很快发现问题：

```text
1. 简单查询能跑，但复杂一点的表达容易选错工具。
2. 用户缺少参数时，模型有时会猜一个参数。
3. 用户在确认阶段说“可以，但数量改成 50”，系统有时只识别“可以”。
4. 工具召回时，相似工具会混淆，例如订单查询和库存查询。
5. 多轮对话里，“它”“这个订单”“刚才那个供应商”容易丢上下文。
6. 有些高风险动作，例如导出、发送邮件、删除，模型会过度推断。
7. 线上问题很难复盘，因为只有最终回答，没有完整中间 trace。
```

所以后续迭代不是单纯“加 prompt”，而是围绕 Agent 工程化做了一轮一轮的闭环。

## 2. 迭代一：工具误触发与非业务请求拦截

### 2.1 线上问题

试点第一周，运营同事在工具窗口里随手输入：

```text
写一首关于春天的诗
```

系统没有直接拒绝，而是尝试进入 ERP 工具选择。有时会选到“查询产品”或“查询库存”这类完全不相关的工具。

类似 bad case 还有：

```text
什么是苹果
介绍一下供应链管理
帮我写一段邮件文案
```

### 2.2 问题发现方式

最初是用户在群里反馈：

```text
为什么我问普通问题，它也要我确认调用工具？
```

我们排查日志发现，问题出在：

```text
工具选择 prompt 默认假设“用户一定要调用 ERP 工具”。
向量召回一定会返回 topK 工具。
LLM 在候选工具中被迫选一个最接近的。
```

### 2.3 技术判断

这不是单个 prompt 的措辞问题，而是路由边界问题。

我的判断是：

```text
不能让工具选择器承担“是否属于工具能力范围”的全部责任。
必须允许系统没有工具可选。
工具选择 prompt 里必须明确允许 None。
评测里必须增加 out-of-scope bad case。
```

### 2.4 工程动作

改造内容：

```text
1. 工具选择 prompt 增加强约束：只能从候选工具或 None 中选择，不能硬选。
2. 如果候选工具相关性不足，返回 no_tool_found。
3. 增加 no_tool_found trace event。
4. 在 eval 中增加非 ERP 请求 case。
5. 指标增加 invalid_tool_call_rate。
```

典型 case：

```text
输入：写一首关于春天的诗
期望：不调用业务工具
输出：该请求不属于 ERP 工具能力范围，无法调用业务工具处理。
```

### 2.5 结果指标

试点集上的变化：

```text
非 ERP 请求误触发工具率：约 18% -> 3%
工具选择准确率：约 76% -> 84%
无效工具调用占比：约 14% -> 5%
```

### 2.6 面试表达

> 第一轮线上问题让我意识到，Agent 不是所有输入都应该进入工具链。最开始我们把“工具选择”当成单点能力，后来拆成了 out-of-scope 判断、候选工具召回和最终工具选择三个层次。这个改造的价值是降低无效工具调用，也让用户知道系统边界。

## 3. 迭代二：参数幻觉与缺参澄清

### 3.1 线上问题

运营人员输入：

```text
帮我创建一笔苹果的订单，数量 50，明天交付
```

创建订单工具实际需要：

```text
productId
quantity
supplierId
deliveryDate
```

问题是用户没有提供 `supplierId`，但模型有时会根据工具描述或历史样例生成一个供应商 ID。

### 3.2 问题发现方式

我们从接口日志里看到一些异常订单：

```text
supplierId=1 出现频率异常高
```

进一步看 trace，发现很多请求里用户根本没有说供应商，模型却抽出了 `supplierId=1`。这说明不是业务 API 的问题，而是参数抽取阶段发生了幻觉。

### 3.3 定位过程

我把问题拆成三类：

```text
1. 用户完全没给参数，模型凭空补。
2. 用户给了模糊参数，例如“常用供应商”，但系统没有长期记忆支撑。
3. 参数格式不合法，例如数量是负数、日期不完整。
```

对应策略不同：

```text
完全没给 -> 缺参澄清
模糊参数 -> 不使用长期记忆自动猜，要求用户补充
格式非法 -> guardrail 拦截
```

### 3.4 工程动作

改造内容：

```text
1. 参数抽取后检查 required 参数。
2. 如果缺必填参数，进入 missing_params_clarify。
3. 用户补充后，用 slot_filling_intent prompt 解析本轮反馈。
4. 后端负责合并参数和再次校验，不让 LLM 直接覆盖执行参数。
5. 对负数、空值、异常大数量做基础 guardrail。
6. 增加 param_extraction eval 和 slot_filling eval。
```

示例流程：

```text
用户：帮我创建一笔苹果的订单，数量 50，明天交付
系统：还需要补充供应商信息才能继续。
用户：供应商用 3
系统：合并 supplierId=3，再进入工具执行确认。
```

### 3.5 结果指标

```text
参数正确率：约 68% -> 86%
缺参识别准确率：约 62% -> 90%
供应商 ID 幻觉 case：明显下降
未确认写操作率：保持为 0
```

### 3.6 面试表达

> 这轮我没有选择继续堆 prompt，让模型“尽量不要编参数”，而是把缺参变成状态机能力。只要 required 参数不完整，就不允许进入工具执行。LLM 只负责解析用户补充的话，最终参数合并和校验由后端做，这样比纯 prompt 更可控。

## 4. 迭代三：HITL 用户反馈理解不稳定

### 4.1 线上问题

系统在执行工具前会让用户确认：

```text
将调用创建订单工具，参数 quantity=20，请确认是否执行。
```

用户回复：

```text
可以，但数量改成 50
```

早期系统有时会只识别到“可以”，然后按旧参数 `quantity=20` 执行。

### 4.2 问题发现方式

这个问题来自用户投诉：

```text
我明明说数量改成 50，为什么还是按 20 下单？
```

我们复盘任务记录，发现系统缺少对 HITL 反馈的结构化解析，只把用户反馈粗略分成：

```text
确认
取消
不明确
```

没有处理“确认 + 参数修改”这种混合意图。

### 4.3 技术判断

这里的核心不是工具选择，而是人类反馈理解。

我当时的判断是：

```text
HITL 不是一个按钮，而是一个自然语言交互状态。
确认阶段不能只看关键词。
只要用户修改参数，就不能直接执行，必须重新确认。
```

### 4.4 工程动作

改造内容：

```text
1. 对 pending_action 做状态分流。
2. missing_params_clarify 走补参解析。
3. tool_execution_confirm 走确认/取消/不明确识别。
4. 对“可以，但数量改成 50”这种 case，识别为参数变更或 unclear，不直接执行。
5. 增加 human_feedback_intent eval。
6. 在线 integration case 中模拟用户多轮反馈。
```

示例：

```text
系统：请确认创建订单，quantity=20
用户：可以，但数量改成 50
系统：不会直接执行，而是要求重新确认或重新规划参数
```

### 4.5 结果指标

```text
HITL 反馈处理准确率：约 70% -> 91%
确认阶段误执行 case：基本清零
用户二次修改参数成功率：显著提升
```

### 4.6 面试表达

> 这轮迭代让我对 HITL 的理解发生了变化。HITL 不是简单的“确认按钮”，而是 Agent 状态机的一部分。用户在确认阶段可能确认、取消、提问、改参数。我们把这些反馈纳入 eval，避免系统因为关键词“可以”就直接执行。

## 5. 迭代四：RAG 工具召回相似工具混淆

### 5.1 线上问题

上线后工具数量从十几个增长到三十多个，出现了相似工具混淆：

```text
查询订单 O-9001
```

有时召回结果里：

```text
query_order
query_inventory
query_product
```

模型会因为订单里包含 productId，误选库存查询。

另一个例子：

```text
查询华东区大客户上个月的对账单
```

可能混淆：

```text
query_reconciliation
export_reconciliation
send_email
```

### 5.2 问题发现方式

这个问题是通过 trace 发现的。用户最终反馈“查错了”，但真正定位要看中间步骤：

```text
召回了哪些工具
LLM 最后选了哪个工具
参数抽取基于哪个工具 schema
最终调用了哪个 operationId
```

没有 trace 时，只看最终回答很难判断错误发生在哪一层。

### 5.3 技术判断

我把工具选择错误拆成：

```text
1. RAG 召回没召到正确工具。
2. 正确工具召到了，但排序靠后。
3. 候选工具都有，LLM 选择错。
4. 用户请求本身包含多个动作，需要拆成链路。
```

不同类型不能用同一个办法解决。

### 5.4 工程动作

改造内容：

```text
1. 优化工具描述：operationId、业务对象、读写属性、适用场景写清楚。
2. 工具选择 prompt 增加“只能选候选工具，不能编造工具”。
3. 针对相似工具增加 tool_selection bad case。
4. 对条件式任务增加 tool_chain eval，例如“库存不足再下单”必须先查库存。
5. 引入权限过滤，用户没有权限的工具不进入候选集。
```

RAG 参数层面的经验：

```text
topK 不能太小，否则正确工具召不到。
topK 也不能太大，否则相似工具太多，LLM 选择噪声增加。
试点阶段 topK 保持在一个中等值，再通过工具描述和 rerank 降低混淆。
```

### 5.5 结果指标

```text
工具选择准确率：约 84% -> 91%
相似工具误选率：约 16% -> 6%
条件式任务链路准确率：约 60% -> 82%
```

### 5.6 面试表达

> 这轮迭代不是简单调 topK。我先判断错误发生在召回、排序、LLM 选择还是任务拆解。最后我们同时做了工具描述治理、候选工具权限过滤、prompt 约束和 tool_selection eval。RAG 在 Agent 里不是只看召回率，还要看召回结果是否会误导 LLM。

## 6. 迭代五：上下文、session 隔离与长对话压缩

### 6.1 线上问题

用户经常多轮操作：

```text
用户：查一下苹果手机 A15 的产品信息。
系统：productId 是 1001。
用户：再查一下它的库存。
```

早期版本依赖前端传上下文。如果刷新页面或者前端没有传足够上下文，后端就不知道“它”指的是苹果手机 A15。

还有一个更严重的问题：

```text
不同用户或不同会话的上下文可能被混用。
```

### 6.2 问题发现方式

用户反馈：

```text
我上一轮明明查的是蓝牙耳机，为什么这轮它查成了苹果手机？
```

排查后发现：

```text
上下文主要由前端传入。
后端没有稳定的 user_id + session_id 隔离。
刷新后会话历史丢失。
长对话时，最近窗口太短会丢中间信息。
```

### 6.3 技术判断

我把记忆分成两层：

```text
短期会话历史：解决当前 session 内的多轮指代。
会话摘要 summary：解决长对话压缩。
```

同时明确不做：

```text
不做长期记忆。
不做 pinned_facts。
不把 summary 当作强参数事实库。
```

原因是 ERP 参数有权限和时效性，不能随便把历史内容当成当前操作参数。

### 6.4 工程动作

改造内容：

```text
1. Task 增加 user_id、session_id、tenant_id。
2. Memory 按 user_id + session_id 隔离。
3. 每轮用户输入和系统输出写入 SessionMemory。
4. ContextManager 构造 bounded context：current_query + recent_messages + summary。
5. 长对话超过窗口后，用 LLM 做 conversation summary compaction。
6. LLM summary 失败时降级为 extractive fallback。
7. trace 记录 summary_compacted。
```

典型链路：

```text
用户：查苹果手机 A15
系统：写入 memory
用户：查它的库存
系统：从当前 session recent messages 找到上一轮产品信息
```

### 6.5 结果指标

```text
多轮上下文追问成功率：约 65% -> 86%
跨 session 串上下文问题：基本消除
长对话 summary fallback 可观测
刷新后会话恢复能力提升
```

### 6.6 面试表达

> 我没有把这个项目包装成完整长期记忆系统，而是先解决最实际的 session memory 和 summary memory。因为 ERP 场景里，长期记忆如果没有权限、过期和来源校验，很容易制造记忆幻觉。我们把 summary 当作上下文压缩，而不是参数事实库。

## 7. 迭代六：权限控制与高风险动作防护

### 7.1 线上问题

财务同事可以查询对账单，但普通运营不应该导出所有客户对账单，更不能发送邮件。

早期系统的问题是：

```text
工具选择阶段只看语义相关性，没有先按用户权限过滤。
如果模型选中了用户无权工具，后面才失败，用户体验差。
```

还有一个 bad case：

```text
用户：帮我导出上个月华东区大客户的对账单
模型候选链路：query_reconciliation -> export_reconciliation -> send_email
```

用户只说导出，没有说发邮件。模型把导出扩展成了外发。

### 7.2 问题发现方式

这个问题来自安全复盘：

```text
虽然最终因为 HITL 没有直接执行，但系统不应该主动提出发送邮件这种外发动作。
```

我们从 trace 里看到：

```text
工具选择阶段已经把 send_email 放进候选链路。
这不是参数问题，而是高风险路由过度推断。
```

### 7.3 技术判断

我把安全控制分成三层：

```text
权限层：用户是否有权调用这个工具。
参数范围层：用户是否能访问这个区域、客户、数据范围。
高风险路由层：用户是否真的表达了导出、外发、删除、批量等动作。
```

其中权限和参数范围必须是确定性逻辑，不能交给 LLM。

高风险路由可以用多提示词交叉验证降低误触发。

### 7.4 工程动作

改造内容：

```text
1. 增加 OperatorContext，包含 user_id、tenant_id、tool_permissions、allowed_regions 等。
2. 工具增加 required_permissions、risk_level、data_domain 等字段。
3. 工具召回后先按权限过滤，用户无权工具不进入 LLM 候选。
4. 工具执行前再次做权限校验，防止参数被篡改。
5. 增加 CrossPromptRouteGuard，只对高风险工具触发多提示词交叉验证。
6. 三个 prompt 分别从显式意图、工具链审计、保守风险角度投票。
7. 增加 route_cross_validation eval。
```

示例：

```text
用户：帮我导出上个月华东区大客户的对账单
工具：exportReconciliation
投票：allow / allow / allow
结果：允许进入 HITL

用户：帮我导出上个月华东区大客户的对账单
工具：sendEmail
投票：clarify / block / block
结果：阻断，原因是用户没有表达发送邮件
```

### 7.5 结果指标

```text
越权工具进入候选集比例：明显下降
高风险工具误触发率：约 9% -> 2%
外发类工具误触发：试点集中未再出现
权限相关 bad case 通过率：接近 100%
```

### 7.6 面试表达

> 这一轮我把“模型有没有选对工具”和“用户有没有权限执行”拆开处理。权限必须是确定性校验，不能靠模型判断。多提示词交叉验证只用于高风险路由，比如导出、外发、删除、批量处理，目的是防止模型把用户的请求扩展成更危险的动作。即便三票通过，最终仍然要经过权限、参数校验和 HITL。

## 8. 迭代七：Trace、Eval 与 bad case 回流

### 8.1 线上问题

项目刚上线时，用户说“它错了”，我们只能看到最终回答，很难知道错在哪里。

Agent 的错误可能发生在：

```text
任务分类
工具召回
工具选择
参数抽取
缺参处理
权限校验
HITL 反馈理解
工具执行
最终总结
```

只看最终答案无法定位问题。

### 8.2 技术判断

我认为 Agent 项目的可维护性依赖两个东西：

```text
Trace：知道每一步发生了什么。
Eval：把线上 bad case 固化成可回归的数据集。
```

没有 trace，只能猜。

没有 eval，改一个 prompt 很容易修好一个 case，又弄坏另一个 case。

### 8.3 工程动作

改造内容：

```text
1. 增加 TraceRecord，记录 task_id、user_id、session_id、模型、工具、参数、HITL、工具结果。
2. 关键事件写入 trace：
   - tool_selected
   - params_extracted
   - missing_params_need_user
   - permission_check_passed / failed
   - route_cross_validation_vote
   - tool_invocation_started / finished
   - answer_grounding_checked
   - summary_compacted
3. 建 prompt eval：
   - tool_selection
   - param_extraction
   - human_feedback_intent
   - slot_filling_intent
   - hallucination_guard
   - route_cross_validation
4. 建 online integration case：
   - happy case
   - bad case
   - HITL case
5. 旧 replay 数据集降级为指标计算器验证，不再伪造 actual trace。
```

### 8.4 bad case 回流机制

线上每出现一个问题，会按这个格式记录：

```text
问题输入
期望行为
实际行为
错误发生阶段
根因分类
修复动作
是否加入 eval
```

例如：

```text
输入：如果库存不够再下单
错误：系统直接进入 create_order
根因：条件式任务拆解错误
修复：tool_chain prompt + bad case
eval：chain_bad_conditional_order_inventory_first
```

### 8.5 结果指标

```text
问题定位时间：从半天级下降到几十分钟
核心 replay eval 通过率：保持在 95% 以上
关键 integration case 可回归
prompt 改动导致旧 case 回归的次数下降
```

### 8.6 面试表达

> Agent 项目上线后最重要的是可观测和可回归。我们不是靠感觉调 prompt，而是把线上问题归因到具体阶段，再决定是改 prompt、改工具描述、改参数校验、改权限逻辑，还是加 HITL。每次改动都要进 eval，防止修一个坏一个。

## 10. 面试官追问准备

### 10.1 如果问：你们怎么发现线上问题？

回答：

> 一开始主要靠用户反馈和接口日志，后来我们补了 TraceRecord，把工具选择、参数抽取、权限校验、HITL、工具执行和最终总结都记录下来。这样每个 bad case 都能定位到具体阶段，例如是召回没召到、工具选错、参数抽错、用户反馈理解错，还是工具执行失败。

### 10.2 如果问：你怎么判断该改 prompt 还是改代码？

回答：

> 我会先做根因分类。如果是模型输出格式不稳定，优先改 prompt 和 parser。如果是缺参、权限、负数、越权这些确定性问题，就必须改代码规则。如果是工具召回混淆，要改工具描述、召回参数或候选过滤。如果是用户反馈理解，就加 HITL 状态机和 eval。不会所有问题都用 prompt 解决。

### 10.3 如果问：如何避免修好一个 case 又弄坏另一个？

回答：

> 每个线上 bad case 都要进 eval dataset，同时保留正向 case 和回归 case。比如为了解决“条件式任务必须先查库存”，不能让普通“查询库存”被过度拆成下单。因此 eval 里同时有 bad_conditional_order 和 regression_simple_inventory。每次改 prompt 或工具链都跑全量 replay。

### 10.4 如果问：多提示词交叉验证是不是很重？

回答：

> 所以我们没有全量使用。普通 read 查询不触发，只有导出、外发、删除、批量、写操作这类高风险工具才触发。它的定位是 L2 风险审计，不替代权限、参数校验和 HITL。这样成本和延迟可控，也更容易评测。

### 10.5 如果问：为什么不直接用 LangGraph？

回答：

> 项目早期是自研轻量状态机，因为试点阶段优先跑通业务闭环。后来我学习 LangGraph 后也复盘过，HITL、checkpoint、session history 这些能力确实可以框架化。但当时我们的核心挑战不是框架本身，而是业务工具边界、权限、参数、eval 和 bad case。后续迁移 LangGraph 是合理方向，但不会改变这些业务治理逻辑。

更稳妥的说法：

## 12. 复盘总结

这个项目最值得强调的不是“我做了一个能调用工具的 Agent”，而是：

```text
我理解 Agent 上线后的问题会发生在链路中间。

我能把 bad case 转成 eval。

```

最终面试主线：

> 这个项目让我真正理解了业务 Agent 的难点不在 demo，而在上线后的持续治理。模型可以生成候选计划，但系统必须有边界、有状态、有权限、有评测、有 trace。我的主要贡献就是把一个能跑 demo 的工具调用系统，逐步迭代成一个可观测、可回归、可控制风险的 ERP Copilot。

## 13. 附录：5 个适合 Agent 开发岗面试讲述的问题案例

下面 5 个案例可以在面试中按需展开。每个案例都刻意体现 Agent 开发岗位关注的能力：工具调用链路分析、Prompt/RAG/参数/记忆/HITL/权限/评测/监控的综合治理。

## 案例一：非 ERP 请求误触发业务工具

### 1. 现象

试点用户在 Copilot 工具窗口里输入：

```text
写一首关于春天的诗
```

系统没有直接拒绝，而是进入工具选择流程，有时会选中“查询产品”或“查询库存”这类业务工具。用户看到系统提示“将调用某某 ERP 工具，请确认”，觉得非常困惑。

类似输入还有：

```text
什么是苹果
帮我写一段邮件文案
介绍一下供应链管理
```

### 2. 影响

这个问题直接影响用户信任。

具体影响是：

```text
无效工具调用占比升高
用户认为系统“不懂边界”
工具确认弹窗变多，人工接管率上升
线上 trace 中出现大量 no-op 或错误候选工具
```

### 3. 定位过程

我先从用户反馈里的原始 query 入手，复现了几条非 ERP 请求。然后查看 tool call trace，发现链路是：

```text
用户输入
-> 工具向量召回
-> topK 一定返回若干工具
-> LLM 被要求从候选工具中选一个
-> 系统进入 HITL 确认
```

继续拆分后发现两个问题：

```text
1. 工具选择 prompt 没有明确允许选择 None。
2. RAG 召回只负责相似度，不负责判断请求是否属于 ERP 工具范围。
```

我还做了一个小的 ablation：

```text
只改 prompt，允许 None。
只改召回阈值。
prompt + no_tool_found trace 一起改。
```

结果发现，仅调召回阈值会误伤一些正常业务请求；更稳的是允许工具选择器显式返回 None，并把 out-of-scope case 加入 eval。

### 4. 根因

根因是系统把“是否应该调用工具”和“从候选工具里选哪个”混在了一步里，而且工具选择 prompt 默认假设用户一定要调用业务工具。

技术上说：

```text
向量召回必然返回近似工具。
LLM 在没有 None 选项时会被迫选择最接近的工具。
非 ERP 请求没有被前置拦截。
```

### 5. 解决方案

我做了几件工程动作：

```text
1. 修改 tool selection prompt，明确允许 action=None。
2. 增加 no_tool_found 分支，不再强制进入工具确认。
3. 增加 no_tool_found trace event，便于统计非业务请求。
4. 在 prompt eval 中加入 out-of-scope bad case。
5. 在集成测试中加入“写春天的诗”这类无效工具调用 case。
6. 增加 invalid_tool_call_rate 指标。
```

### 6. 结果

试点回归集上的结果：

```text
非 ERP 请求误触发工具率：约 18% -> 3%
无效工具调用占比：约 14% -> 5%
工具选择准确率：约 76% -> 84%
用户反馈中“莫名弹出工具确认”的问题明显减少
```

### 7. 面试表达方式

> 我们上线后遇到的第一个典型问题是非业务请求误触发工具。比如用户在工具窗口里输入“写一首关于春天的诗”，系统竟然会尝试调用库存或产品查询工具。我通过 trace 发现，问题不是某一个工具错了，而是工具选择链路默认一定要选一个工具，RAG topK 也一定会返回候选。我的处理不是简单调相似度阈值，因为那会误伤正常请求，而是让工具选择 prompt 支持 None，并增加 no_tool_found 分支和 out-of-scope eval。改完后，非 ERP 请求误触发率从大概 18% 降到 3%，也让用户知道系统边界在哪里。

## 案例二：创建订单时模型凭空补供应商 ID

### 1. 现象

用户输入：

```text
帮我创建苹果的订单，数量 50，明天交付
```

创建订单工具需要：

```text
productId
quantity
supplierId
deliveryDate
```

但用户没有提供供应商。线上日志里却出现了很多 `supplierId=1` 的订单参数。

### 2. 影响

这个问题影响很严重，因为它不是答错一句话，而是可能导致错误业务操作。

具体影响：

```text
订单参数不可信
人工确认时用户不一定能发现 supplierId 是模型猜的
业务人员对系统下单能力失去信任
写操作风险上升
```

### 3. 定位过程

我先从异常参数入手，统计了一段时间内创建订单请求里的 `supplierId` 分布，发现 `supplierId=1` 异常集中。

然后回看 trace：

```text
原始 query 没有供应商
参数抽取结果却有 supplierId
工具 schema 里 supplierId 是 required
模型输出中没有说明该参数来源
```

我又构造了几组测试：

```text
完全不提供供应商
提供“常用供应商”
提供“华东供应商”
明确提供 supplierId=3
```

对比 prompt 版本后发现，旧 prompt 里强调“尽量补全参数”，模型会倾向于从示例或上下文中猜一个值。

### 4. 根因

根因是参数抽取 prompt 对“必填参数”处理过于激进，没有把“抽不到”和“猜一个”严格区分。

技术上说：

```text
required 参数缺失时，系统没有进入澄清状态。
LLM 被鼓励补全参数。
后端没有对缺参进行确定性阻断。
```

### 5. 解决方案

我做了以下改造：

```text
1. 参数抽取后对 required 参数做确定性检查。
2. 缺少 supplierId 时，不允许进入工具执行确认。
3. 增加 pending_action=missing_params_clarify。
4. 用户补充后，用 slot_filling_intent prompt 只解析本轮补充内容。
5. 后端合并参数，并再次校验 required、类型、枚举。
6. 增加 param_extraction eval 和 slot_filling eval。
7. 将“缺供应商不能编造”加入 bad case 回归集。
```

### 6. 结果

回归集和试点 trace 上的结果：

```text
参数正确率：约 68% -> 86%
缺参识别准确率：约 62% -> 90%
供应商 ID 幻觉 case 明显下降
未确认写操作率保持 0
```

### 7. 面试表达方式

> 我们上线后发现一个比较典型的参数幻觉问题：用户创建订单时没有说供应商，但模型会给出 supplierId，尤其是 supplierId=1 出现频率很高。我没有只改 prompt 让模型“不要乱猜”，而是把 required 参数检查放到后端流程里。只要必填参数缺失，就进入 missing_params_clarify，让用户补充。LLM 只负责解析用户补充的那句话，参数合并和校验由后端做。这样参数正确率从 68% 提升到 86%左右，供应商 ID 幻觉明显减少。

## 案例三：HITL 阶段“可以，但数量改成 50”被误判为确认

### 1. 现象

系统提示用户确认：

```text
将调用创建订单工具，参数 quantity=20，请确认是否执行。
```

用户回复：

```text
可以，但数量改成 50
```

早期版本有时只识别到“可以”，然后按旧参数 `quantity=20` 执行。

### 2. 影响

这个问题影响 HITL 的可信度。

具体影响：

```text
用户以为自己修改了参数，系统却按旧参数执行
人工确认机制形同虚设
写操作安全风险升高
用户需要人工回滚或重新下单
```

### 3. 定位过程

我先查看对话日志，确认用户确实在确认阶段提出了参数修改。

然后看 tool call trace：

```text
pending_action=tool_execution_confirm
curr_tool_param.quantity=20
human_feedback=可以，但数量改成 50
intent=confirm
tool_invocation_started.quantity=20
```

这个 trace 说明错误不是参数抽取阶段，而是 HITL 反馈理解阶段。

我对比了几种用户反馈：

```text
立即执行
不执行
这个参数是什么意思
可以，但数量改成 50
供应商也换成 3
```

发现旧逻辑主要依赖确认关键词，“可以”权重过高，没有识别混合意图。

### 4. 根因

根因是 HITL 反馈被简化成二分类：

```text
确认
取消
```

实际确认阶段用户可能：

```text
确认执行
取消执行
提问
修改参数
补充条件
```

系统没有把“确认 + 参数修改”作为独立风险处理。

### 5. 解决方案

工程动作：

```text
1. 引入 pending_action 分流，不同等待状态走不同处理逻辑。
2. 为 HITL 反馈增加 human_feedback_intent prompt。
3. 对“可以，但数量改成 50”这类反馈，不直接执行。
4. 如果识别为参数修改或 unclear，继续等待或重新规划。
5. 增加 human_feedback_intent eval。
6. 在线集成测试中模拟多轮 HITL：确认、取消、不明确、补参数、改参数。
```

### 6. 结果

```text
HITL 反馈处理准确率：约 70% -> 91%
确认阶段误执行 case 基本清零
用户二次修改参数成功率明显提升
unsafe_execution_rate 保持 0
```

### 7. 面试表达方式

> 我们曾经遇到一个 HITL 相关的线上问题，用户在确认阶段说“可以，但数量改成 50”，系统却只识别“可以”，按旧的 20 执行了。这个问题让我意识到 HITL 不是一个简单按钮，而是 Agent 状态机的一部分。用户在确认阶段可能确认、取消、提问或者改参数。我通过 trace 定位到错误发生在 human feedback intent，而不是参数抽取。后面我们增加了 pending_action 分流和 HITL 反馈 eval，对混合意图不再直接执行。改完后 HITL 反馈处理准确率提升到 90%以上。

## 案例四：RAG 工具召回中相似工具混淆

### 1. 现象

工具数量增加后，用户输入：

```text
查询订单 O-9001
```

系统有时召回并选择了库存查询工具，而不是订单查询工具。

另一个类似问题：

```text
查询华东区大客户上个月的对账单
```

可能混淆：

```text
query_reconciliation
export_reconciliation
send_email
```

### 2. 影响

```text
工具调用准确率下降
多步骤任务链路跑偏
用户得到答非所问的结果
后续参数抽取也会基于错误 schema 继续错
```

### 3. 定位过程

我先复现用户输入，然后查看 tool call trace：

```text
query
召回 topK 工具列表
每个工具的 description
LLM 最终选择
参数抽取结果
最终 operationId
```

我把错误拆成四类：

```text
1. 正确工具没有被召回。
2. 正确工具召回了，但排序靠后。
3. 候选工具都有，但 LLM 选错。
4. 用户请求本身是多动作任务，需要拆链。
```

然后做 ablation：

```text
调整 topK
优化工具 description
增加 operationId 和业务对象描述
加入 rerank 前后的对比
修改 tool selection prompt
```

结果发现，只调 topK 不稳定。topK 太小会漏召回，太大会给 LLM 太多相似工具，反而增加误选。

### 4. 根因

根因是工具 schema 和工具描述不够区分业务边界。

例如：

```text
订单查询工具描述里包含 productId。
库存查询工具描述里也包含 productId。
LLM 看到 productId 后容易把订单查询误判成库存查询。
```

另外，RAG 召回关注语义相似，不理解业务动作边界。

### 5. 解决方案

工程动作：

```text
1. 重写工具描述，明确业务对象、动作、读写属性和适用场景。
2. tool selection prompt 强化“只能从候选工具中选，不能编造”。
3. 增加 None 选项，避免硬选。
4. 对用户无权限工具做候选集过滤。
5. 针对相似工具建立 tool_selection golden set。
6. 对条件式任务建立 tool_chain eval，例如“库存不足再下单”必须先查库存。
7. 对导出、外发等高风险相似链路增加 route_cross_validation。
```

### 6. 结果

```text
工具选择准确率：约 84% -> 91%
相似工具误选率：约 16% -> 6%
条件式任务链路准确率：约 60% -> 82%
tool_selection replay 通过率保持 95% 以上
```

### 7. 面试表达方式

> 工具数量增长后，我们遇到过 RAG 工具召回相似工具混淆的问题。比如用户查订单，系统有时选了库存查询。我的排查方式是看 trace 里的 topK 候选、工具描述、LLM 最终选择和参数 schema。我发现问题不只是 topK，而是工具描述没有清楚表达业务动作边界。后来我优化了 tool schema，增加读写属性、业务对象和适用场景，同时建立 tool_selection golden set 和 tool_chain eval。这个改造后，相似工具误选率从 16%左右降到 6%左右。

## 案例四补充：RAG 检索调试、索引和 rerank 调优故事

这一节专门用于回答面试官可能追问的 RAG 细节：

```text
RAG 这部分你是怎么调试的？
选择了什么索引？
调了哪些参数？
遇到过什么困难？
rerank 用的什么模型？为什么选它？
```

这里的 RAG 不是传统知识库问答，而是“工具检索 RAG”。它的目标不是把一篇文档召回给模型回答，而是从几十个 ERP 接口描述里召回最相关的候选工具，再交给 rerank 和 LLM 做最终选择。

实际链路可以这样讲：

```text
OpenAPI 工具解析
-> 工具结构化信息存 MongoDB
-> operationId + name_for_human + description 生成 operation_summary
-> operation_summary 向量化后写入 Milvus
-> 用户 query 向量检索召回 topK * 2
-> gte-rerank-v2 对候选工具精排
-> 取 rerank 后 topK 交给 LLM 最终选择
-> 参数抽取、权限校验、HITL、工具执行
```

### 小故事一：为什么选择 Milvus AUTOINDEX + COSINE

#### 背景

最开始工具数量只有十几个，直接把所有工具描述塞进 prompt 也能跑。但随着试点范围扩大，接口增长到三十多个，后续还可能扩展到五十个以上。如果每次把所有工具都放进 prompt，会带来两个问题：

```text
1. prompt 变长，成本和延迟上升。
2. 相似工具太多，LLM 更容易被无关工具干扰。
```

所以我们把工具选择拆成两段：

```text
第一段：Milvus 做向量召回，缩小候选集。
第二段：rerank + LLM 在候选集里做精排和选择。
```

#### 问题

一开始我纠结过要不要手动选 HNSW、IVF_FLAT、FLAT 这类索引。后来结合业务规模判断：我们的工具数量不是百万级知识库，而是几十个 ERP API 工具。这个场景下，索引本身不是主要瓶颈，真正影响准确率的是：

```text
工具文本怎么构造
topK 取多大
rerank 是否能把正确工具排到前面
LLM 是否能理解候选工具边界
```

#### 思考

因此我没有把大量精力放在复杂索引调参上，而是选择了更稳妥的 Milvus `AUTOINDEX + COSINE`：

```text
index_type：AUTOINDEX
metric_type：COSINE
embedding 维度：1024
search_params：level=1
collection：tools
主键：tool_id
向量字段：embedding
文本字段：operation_summary
```

如果面试官追问 Milvus 这些索引到底是什么，可以用下面这个口径解释：

```text
FLAT：
暴力精确检索，不做近似索引。优点是召回最稳，缺点是数据量大时慢。适合小数据集、强过滤后候选很少、或者要求极高召回的场景。

AUTOINDEX：
把索引选择交给 Milvus，根据当前版本和部署环境自动选择较合适的索引策略。优点是少调参、上线风险低；缺点是可解释性和精细控制不如手动指定 HNSW/IVF。

IVF_FLAT：
倒排文件索引。先把向量聚成多个簇，查询时只扫描最相关的若干簇。常见参数是 nlist 和 nprobe。优点是大规模数据上速度快；缺点是 nprobe 太小会漏召回，太大又接近暴力检索。

IVF_SQ8：
IVF + 8 bit 标量量化。把每个维度压缩成更小的表示，节省内存。优点是成本低；缺点是量化有损，召回和排序精度可能下降。

IVF_PQ：
IVF + 产品量化。把向量切成多个子空间分别编码，压缩率更高。适合内存很紧或向量规模很大；缺点是精度损失通常比 IVF_FLAT 更明显，调参成本也更高。

HNSW：
图索引。把向量组织成多层近邻图，查询时沿图快速跳转。常见参数是 M、efConstruction、efSearch。优点是低 topK、高召回、低延迟；缺点是建索引慢、内存占用更高。

HNSW_SQ / HNSW_PQ：
HNSW 叠加量化。目的是降低内存占用，但会引入一定精度损失。适合数据量较大、又希望保留 HNSW 查询速度的场景。

DISKANN：
磁盘型近邻图索引，面向数据量很大、内存放不下、但有 SSD 的场景。优点是容量友好；缺点是会受磁盘 I/O 影响，不适合我们这种几十个工具的小规模召回。

SCANN：
面向高性能近似检索的索引方案，通常通过分区、量化和重排做速度与召回折中。适合更大规模检索，不是本项目的主要矛盾。

GPU_IVF_FLAT / GPU_IVF_PQ / GPU_BRUTE_FORCE / GPU_CAGRA：
GPU 加速索引，适合高并发、大规模向量检索。我们工具库规模很小，引入 GPU 索引反而增加部署复杂度。

SPARSE_INVERTED_INDEX：
稀疏向量索引，更像 BM25/稀疏检索的方向。适合关键词匹配很重要的场景，可以和 dense embedding 做 hybrid search，但本项目第一阶段没有做混合检索。

INVERTED / BITMAP / Trie：
这些更多是标量字段索引，不是 dense vector 主索引。例如按 tenant_id、tool_permission、risk_level 做过滤时可以用，但不承担语义召回。
```

这里有一个关键判断：

```text
如果是百万级知识库，索引选择会直接影响召回、延迟和成本。
但本项目是几十个工具描述的工具 RAG，索引不是瓶颈。
因此我们没有把复杂度放在 HNSW/IVF 参数上，而是先用 AUTOINDEX + COSINE 保证工程稳定，再把精力放在工具描述、topK、rerank 和 eval 上。
```

选择 `COSINE` 的原因是工具检索本质是语义相似度匹配，用户 query 和工具描述的长度差异较大，用方向相似度比直接欧氏距离更符合这个场景。

选择 `AUTOINDEX` 的原因是：

```text
1. 工具规模较小，召回延迟不是瓶颈。
2. Milvus 自动索引能减少手动参数不当带来的不稳定。
3. 项目重点是 Agent 工具链闭环，不是专门做大规模向量库调优。
4. 后续如果工具规模上升，可以再切换 HNSW 或 IVF，并围绕 recall/latency 做专项调参。
```

#### 解决

我的落地做法是：

```text
1. 一个工具对应一个向量 chunk，不把一个接口再切成多个文档。
2. 向量库只存 tool_id、operation_summary 和 embedding。
3. 工具完整 schema、权限、风险等级仍然存在 MongoDB。
4. Milvus 只负责召回候选工具 ID。
5. 召回后再回 MongoDB 拿完整工具信息。
```

这里故意没有把所有参数值、枚举值、示例全部塞进向量文本。因为工具 RAG 的核心是判断“该用哪个工具”，不是在向量库里完成参数抽取。参数抽取应该在选定工具 schema 之后做。

#### 效果

试点阶段这个选择比较稳：

```text
向量召回延迟稳定在可接受范围内
正确工具进入候选集的比例提升到 95% 左右
没有因为索引调参引入额外不确定性
把主要优化精力集中在工具描述、topK、rerank 和 eval 上
```

#### 面试表达方式

> 我们的 RAG 不是大规模知识库，而是工具检索，规模是几十个 ERP API。这个场景下我没有上来就做复杂 HNSW 或 IVF 调参，而是用 Milvus AUTOINDEX + COSINE，先保证稳定召回。因为真正影响工具选择准确率的不是索引算法本身，而是工具文本构造、topK、rerank 和后面的 LLM 选择。向量库只存 tool_id 和 operation_summary，完整 schema 仍然从 MongoDB 取，这样职责比较清楚。

### 小故事二：topK 和候选池大小怎么调

#### 背景

RAG 调试里最容易被问到的参数就是 `topK`。我们的工具召回不是直接取 topK 给模型，而是采用两阶段候选池：

```text
Milvus 向量召回：topK * 2
rerank 精排：取最终 topK
LLM 工具选择：只看 rerank 后候选工具
```

例如最终希望给 LLM 5 个候选工具，就先从 Milvus 召回 10 个，再由 rerank 排序后取前 5 个。

#### 问题

线上 bad case 暴露出两个相反的问题：

```text
topK 太小：
正确工具可能根本没有进入候选集。

topK 太大：
候选工具里相似接口太多，LLM 反而更容易误选。
```

比如：

```text
用户：查询订单 O-9001
正确工具：query_order
干扰工具：query_inventory、query_product、query_order_item
```

如果 topK=3，某些表达下 `query_order` 可能没进候选。

如果 topK=10，候选里会有很多订单、库存、商品相关工具，LLM 看到 `productId`、`orderId`、`skuId` 等字段后容易混淆。

#### 思考

我当时没有只看最终工具选择准确率，而是把指标拆开：

```text
candidate_recall：正确工具是否进入 Milvus 候选集
rerank_top1：rerank 后正确工具是否排第一
rerank_mrr：正确工具在 rerank 结果中的平均倒数排名
final_tool_accuracy：LLM 最终选中的工具是否正确
invalid_tool_call_rate：是否误触发不该调用的工具
```

拆开之后就能看出问题发生在哪一层。

#### 解决

我做了一组小规模调参实验：

```text
方案 A：最终 topK=3，Milvus 召回 6 个
优点：候选少，LLM 干扰小
问题：复杂表达下容易漏召回

方案 B：最终 topK=5，Milvus 召回 10 个
优点：召回和干扰之间比较平衡
问题：需要 rerank 稳住排序

方案 C：最终 topK=8，Milvus 召回 16 个
优点：候选召回更全
问题：prompt 更长，相似工具更多，LLM 误选率上升
```

最终试点阶段选择的是中间方案：

```text
Milvus 召回 topK * 2
rerank 后返回 topK
工具选择 prompt 中明确允许 None
```

这样做的好处是，Milvus 先保证不漏，rerank 再过滤噪声，LLM 不直接面对过大的候选集。

#### 效果

调参后的模拟指标可以这样讲：

```text
候选集召回率：约 88% -> 96%
rerank 后正确工具 Top1：约 76% -> 88%
最终工具选择准确率：约 84% -> 91%
相似工具误选率：约 16% -> 6%
```

#### 面试表达方式

> RAG 调参时我没有只调一个 topK，而是把召回、rerank 和最终选择拆开看。我们最后采用的是 Milvus 先召回 topK 的两倍，再用 rerank 压到最终 topK。topK 太小会漏召回，太大会给 LLM 太多相似工具，所以最终取了一个折中值，比如召回 10 个、精排到 5 个。这个策略让正确工具进入候选集的比例提高，同时不会让 LLM 被过多候选干扰。

### 小故事三：rerank 用什么，为什么选择 gte-rerank-v2

#### 背景

只靠向量召回时，工具候选经常是“差不多相关”，但排序不够稳定。比如：

```text
用户：查询华东区大客户上个月的对账单
候选工具：
1. query_reconciliation
2. export_reconciliation
3. query_customer
4. send_email
```

这些工具在语义上都和“客户、对账单、华东区”有关，但用户真正要的是查询，不是导出，也不是发邮件。

#### 问题

向量召回的问题是，它更擅长粗粒度语义相似，不擅长判断细粒度动作差异：

```text
查 vs 导出
查询订单 vs 查询订单明细
查询库存 vs 查询商品
查询对账单 vs 发送对账邮件
```

这些差异对业务工具调用非常关键。

#### 思考

我评估过两类 rerank：

```text
本地 reranker：
例如 bge-reranker-v2-m3，优点是可私有化，缺点是要考虑模型部署、显存、并发和冷启动。

API reranker：
例如通义千问 gte-rerank-v2，优点是中文语义和业务短文本排序效果较好，接入快，能返回 relevance_score。
```

考虑到试点阶段工具数量不大、主要语言是中文、团队更关注 Agent 链路闭环，我选择了 `gte-rerank-v2` 作为主 reranker。

更具体一点，当时对比过下面几类模型：

```text
1. gte-rerank-v2
定位：通义系文本 rerank，适合文本语义检索和 RAG 精排。
优点：中文业务短文本排序效果稳定，DashScope SDK 接入简单，当时团队已有阿里云 API Key 和调用链路；支持返回 relevance_score，便于做 trace 和 eval。
缺点：属于外部 API，存在网络延迟；今天看已经不是最推荐的新模型，后续需要迁移。
结论：试点阶段主选。

2. qwen3-rerank
定位：更新一代通义文本 rerank，面向文本语义检索和 RAG 应用。
优点：语种覆盖更广，支持 instruct，可以用一句任务指令告诉模型“这是工具选择 rerank，不是普通问答检索”。
缺点：接口格式和旧 text-rerank API 不完全一致，需要改适配层；在当时试点阶段，工具库只有几十个，收益没有大到必须立刻替换。
结论：作为后续升级方向；如果今天重新上线，会优先考虑它。

3. qwen3-vl-rerank
定位：多模态 rerank，支持文本、图片、视频混合排序。
优点：适合图片检索、跨模态搜索。
缺点：我们的候选是 OpenAPI 工具描述，完全是文本，没有图片或视频；用它会增加成本和复杂度。
结论：排除。

4. bge-reranker-v2-m3
定位：开源本地 reranker，多语言能力不错，可私有化部署。
优点：适合甲方要求内网部署、数据不能出域、长期成本可控的场景。
缺点：需要额外模型服务、GPU/CPU 推理资源、监控和扩缩容；试点阶段工程成本更高。
结论：作为私有化备选，不作为第一版主链路。

5. Jina / Cohere 等外部 rerank 服务
定位：成熟的商业 rerank API。
优点：效果和工程体验通常不错。
缺点：国内企业 ERP 场景下会涉及数据出境、网络稳定性、采购和合规流程，不适合作为第一选择。
结论：只做思路参考，没有进入落地方案。
```

所以最终选择 `gte-rerank-v2` 不是因为它理论上永远最好，而是因为它在当时满足试点阶段的几个硬条件：

```text
中文 ERP 短文本效果够用
接入成本低
能返回 relevance_score 做 trace
团队已有 DashScope 调用经验
几十个候选工具下延迟可控
失败时可以降级到 Milvus 原始排序
```

如果按今天的生产方案复盘，我会补一句：

```text
现在官方已经推荐使用 qwen3-rerank 替代旧的 gte-rerank 系列。
所以线上长期演进会把 reranker 包一层统一接口，先保留 gte-rerank-v2 兼容历史链路，再灰度迁移到 qwen3-rerank。
灰度指标看 rerank_mrr、final_tool_accuracy、P95 延迟和 rerank_error_rate。
```

如果面试官追问为什么不用本地 BGE，可以这样说：

```text
BGE 是备选方案，适合私有化和成本稳定要求更强的场景。
试点阶段为了快速验证工具选择链路，用 gte-rerank-v2 更省工程成本。
如果后续甲方要求全链路私有化，可以把 reranker 替换成本地 bge-reranker-v2-m3，接口层保持不变。
```

#### 解决

工程上 rerank 的输入不是完整 OpenAPI，而是候选工具短文本：

```text
query：用户当前任务描述
documents：候选工具的 name_for_human + description
model：gte-rerank-v2
top_n：候选工具数量
返回：候选工具索引顺序和 relevance_score
```

同时做了两个保护：

```text
1. rerank 只处理 Milvus 召回的 topK * 2，控制延迟和成本。
2. rerank API 异常时，降级使用 Milvus 原始排序，不让整个工具链中断。
```

#### 遇到的困难

困难主要有三个：

```text
1. rerank 分数相近时，模型仍然可能把“查询”和“导出”排得很近。
2. 工具 description 写得太泛时，rerank 也没有足够信息区分。
3. API rerank 会带来额外延迟，所以不能对所有工具全量 rerank。
```

所以 rerank 不是万能的，它必须配合工具描述治理和候选池控制。

#### 效果

加入 rerank 后，比较明显的改善是：

```text
正确工具在候选中的平均排名提升
相似工具误选减少
LLM 最终选择的候选质量更稳定
工具选择 prompt 的压力下降
```

模拟指标可以这样讲：

```text
正确工具 Top1 排名：约 76% -> 88%
MRR：约 0.81 -> 0.92
相似工具误选率：约 16% -> 6%
```

#### 面试表达方式

> 我们 rerank 用的是通义千问的 gte-rerank-v2。选择它主要是因为工具描述和用户 query 都是中文业务短文本，gte-rerank-v2 在这种语义排序上效果比较稳定，而且接入成本低，能快速验证链路。我们没有全量 rerank 所有工具，而是 Milvus 先召回 topK 的两倍，再 rerank 到最终 topK。rerank 失败时会降级使用向量原始排序。后续如果甲方要求私有化，可以平滑替换成本地 bge-reranker-v2-m3。

### 小故事四：真正难调的不是索引，而是工具描述

#### 背景

调试 RAG 时我一开始也想着是不是索引没选好、topK 没调好。但复盘 trace 后发现，很多问题不是向量库没有召回正确工具，而是候选工具描述太像。

例如两个工具：

```text
query_order：根据订单号查询订单信息，包含商品、数量、供应商等字段。
query_inventory：根据商品或 SKU 查询库存信息，包含商品、数量、仓库等字段。
```

用户说：

```text
查一下订单 O-9001 里苹果手机的数量
```

这个 query 同时包含“订单”“商品”“数量”，两个工具都会相似。

#### 问题

如果工具描述只是从 OpenAPI 自动拿 `summary` 和 `description`，经常会出现这些问题：

```text
1. 描述太短，只写“查询订单”“查询库存”。
2. 描述太泛，所有接口都写“用于查询业务信息”。
3. 缺少不适用场景，例如查询对账单不等于导出对账单。
4. 只写字段名，没有写业务动作边界。
5. 中文业务同义词缺失，例如“账差”“差异”“对账异常”。
```

这些问题不是调索引能彻底解决的。

#### 思考

我把工具描述当成“工具卡片”治理，而不是直接相信 OpenAPI 原始描述。一个好的工具卡片至少要包含：

```text
operationId：稳定的技术名称
name_for_human：中文业务名称
business_object：业务对象，例如订单、库存、对账单
action：查询、创建、更新、删除、导出、发送
read_write：读操作还是写操作
when_to_use：什么时候应该用
when_not_to_use：什么时候不应该用
required_params：关键必填参数
domain_terms：业务同义词
```

但在向量索引里不一定要把这些字段都拆开存。更实用的做法是把这些信息治理到 `description` 里，让 `operation_summary` 有足够区分度。

#### 解决

我做了三类工具描述治理：

```text
第一类：动作边界
把“查询对账单”和“导出对账单”分清楚。

第二类：对象边界
把“订单主表”“订单明细”“商品库存”“商品档案”分清楚。

第三类：风险边界
把“查询”“导出”“发送邮件”“批量更新”分清楚。
```

示例：

```text
优化前：
查询对账单信息。

优化后：
查询客户对账单及账差明细。适用于用户只想查看对账结果、账差原因、应收应付金额的场景。不用于导出文件，不用于发送邮件，不执行外发动作。
```

#### 效果

工具描述治理后，rerank 和 LLM 的判断都更稳定：

```text
query_reconciliation 和 export_reconciliation 的混淆明显下降
订单主表和订单明细的混淆下降
高风险外发工具不再因为语义相近频繁进入最终候选
```

可以用这个指标表达：

```text
工具召回正确但 LLM 误选的 case：下降约 40%
相似工具 bad case 通过率：约 72% -> 93%
```

#### 面试表达方式

> RAG 调试时我发现，很多问题不是索引没选好，而是工具描述没有业务边界。比如查询对账单、导出对账单、发送对账邮件在词面上都很接近，但业务风险完全不同。后来我把 OpenAPI 原始描述治理成工具卡片，补充动作、对象、读写属性、适用和不适用场景。这个改造比单纯调 topK 更有效，因为它给 embedding、rerank 和 LLM 都提供了更清楚的判断依据。

### 小故事五：RAG 问题如何靠 trace 和 eval 闭环

#### 背景

早期用户反馈“工具选错了”，如果只看最终回答，很难判断错误发生在哪里。Agent 链路太长，工具选错可能有多种根因：

```text
向量没召回
rerank 排错
LLM 在候选里选错
权限过滤后正确工具被排除
用户请求其实是多工具链路
参数抽错导致看起来像工具错
```

#### 问题

如果没有 trace，每次都只能凭感觉改 prompt。结果经常出现：

```text
修好了一个 case，另一个 case 又坏了。
topK 调大后召回好了，但 LLM 误选增加。
prompt 改保守后无效调用少了，但正常业务也被拒绝。
```

#### 思考

我把 RAG 调试拆成一个定位表：

```text
正确工具没进 Milvus 候选：
优先看 embedding、operation_summary、topK、索引是否重建。

正确工具进了候选但 rerank 靠后：
优先看 rerank 输入文本、工具描述差异、同义词覆盖。

正确工具 rerank 靠前但 LLM 没选：
优先看 tool selection prompt、候选工具格式、None 规则。

LLM 选对工具但参数错：
问题转到参数抽取和 schema 校验，不归因到 RAG。

正确工具被权限过滤掉：
检查用户权限上下文和 required_permissions 配置。
```

#### 解决

我在 trace 里重点记录这些信息：

```text
原始 query
Milvus 召回 tool_id 列表
召回工具的 operation_summary
rerank 前后排序
rerank relevance_score
权限过滤前后的候选工具
LLM 最终选择的 operationId
参数抽取结果
最终工具执行结果
```

然后把线上 bad case 放入 RAG golden set：

```text
库存查询类
订单查询类
订单明细类
对账单查询类
导出类
邮件外发类
条件式多步骤类
非 ERP out-of-scope 类
```

每次改工具描述、topK、prompt 或 rerank，都跑同一批 case，观察：

```text
candidate_recall
rerank_mrr
final_tool_accuracy
invalid_tool_call_rate
no_tool_found_accuracy
```

#### 遇到的困难

这里最大的困难是指标之间会互相拉扯：

```text
提高召回率，可能引入更多噪声。
降低无效调用，可能让正常请求被判 None。
工具描述写得太详细，可能把参数噪声带进召回。
rerank 变强，仍然挡不住 LLM 对高风险动作的过度推断。
```

所以最后不是追求单一指标最高，而是看整条工具调用链路：

```text
正确工具能进候选
正确工具能排前面
LLM 不编造工具
权限和 HITL 能兜底
最终执行结果能被 trace 复盘
```

#### 效果

这套 trace + eval 闭环带来的价值是：

```text
RAG 问题定位从“猜 prompt”变成“按链路归因”
每次调参都有回归集验证
线上 bad case 能沉淀成长期资产
工具数量增加时，仍然能控制相似工具混淆
```

可以这样给结果：

```text
RAG 相关问题平均定位时间：从半天级下降到几十分钟
RAG golden set 通过率：约 78% -> 93%
工具调用准确率：约 84% -> 91%
```

#### 面试表达方式

> 我调 RAG 时不是只看最终回答，而是把 trace 打开看每一层：Milvus 召回了什么、rerank 怎么排、LLM 为什么选这个工具、参数是否基于正确 schema 抽取。这样可以把问题分清楚：是没召回、排序错、LLM 选错，还是参数抽取错。每次线上 bad case 都会进入 RAG golden set，之后改 topK、工具描述或 prompt 都跑回归。这个过程让 RAG 调试从经验改 prompt 变成了可定位、可评测、可回归的工程流程。

## 案例五：多轮上下文丢失导致“它”的指代错误

### 1. 现象

用户连续操作：

```text
用户：查一下苹果手机 A15 的产品信息。
系统：苹果手机 A15 的 productId 是 1001。
用户：再查一下它的库存。
```

早期版本有时不知道“它”指什么，或者在刷新页面后丢失上一轮上下文。

更严重的情况是，不同用户或不同 session 的上下文可能被混用。

### 2. 影响

```text
多轮任务成功率下降
上下文追问体验差
用户需要重复输入完整信息
存在 session 串用风险
参数可能来自错误上下文
```

### 3. 定位过程

我先复现多轮对话，分别测试：

```text
不刷新页面
刷新页面
不同用户
同一用户不同 session
长对话超过上下文窗口
```

然后检查上下文构造逻辑：

```text
前端是否传 contexts
后端是否有 session memory
contextNumber 是多少
recent messages 是否包含上一轮
summary 是否更新
任务里是否记录 user_id 和 session_id
```

排查发现，早期版本主要依赖前端传上下文；如果刷新、切换页面或 contextNumber 太小，后端就拿不到足够历史。

### 4. 根因

根因是上下文管理没有后端状态化。

具体来说：

```text
上下文主要依赖前端。
后端没有稳定的 user_id + session_id 隔离。
长对话没有 summary compaction。
recent window 太小时，中间关键信息容易丢失。
```

### 5. 解决方案

工程动作：

```text
1. Task 增加 user_id、session_id、tenant_id。
2. SessionMemory 按 user_id + session_id 隔离。
3. 每轮用户输入和系统输出都写入后端 memory。
4. ContextManager 构造 bounded context：current_query + recent_messages + summary。
5. recent_messages 至少保留最近 6 条。
6. 长对话超过窗口后，用 LLM 做 conversation summary compaction。
7. LLM summary 失败时降级为 extractive fallback。
8. trace 记录 summary_compacted。
9. 增加 context_follow_up_inventory 这类集成测试。
```

### 6. 结果

```text
多轮上下文追问成功率：约 65% -> 86%
跨 session 串上下文问题基本消除
刷新后继续对话能力提升
长对话 summary fallback 可观测
```

### 7. 面试表达方式

> 多轮上下文是上线后暴露比较明显的问题。用户先查苹果手机 A15，下一轮说“查一下它的库存”，早期系统如果前端没传足上下文，就不知道“它”是谁。我通过复现刷新、不同用户、不同 session 和长对话场景，发现问题是上下文主要依赖前端，后端没有稳定的 session memory。后面我加了 user_id/session_id 隔离、SessionMemory、ContextManager 和 summary compaction。这里我刻意没有做长期记忆，因为 ERP 参数有权限和时效性，summary 只做上下文压缩，不当成强参数事实库。改完后多轮追问成功率从 65%左右提升到 86%左右。
